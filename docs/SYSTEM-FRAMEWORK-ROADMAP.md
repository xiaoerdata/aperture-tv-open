# 下一阶段：小米电视系统框架

记录日期：2026-10-25（Asia/Shanghai）。依据产品提示 P36–P38。本文是架构决策与研究记录，新能力均为规划；现有 Alpha 的能力和验收边界仍以 [兼容检查](XIAOMI-COMPATIBILITY.md) 与 [下载说明](DOWNLOADS.md) 为准。

## 核心目标

从家庭屏应用迭代为能够承担部分电视系统职责的开源框架：桌面、应用入口与管理、家庭通知、NAS 媒体、设备能力和 Agent 编排。仅适配小米电视，Android 8+ 是安装下限；具体系统能力按型号与固件验证。

APK 可以继续作为安装和更新载体。框架化的实质是稳定的能力契约、生命周期、设备适配和故障恢复，不能通过改名或增加设置页面宣称已经替代 ROM。

保留小爱语音键、远场唤醒、小米账号、米家、音量、电源和输入源的原生路线。先承接日常交互与家庭服务，系统权限扩展作为明确分支推进；不以停用小米桌面或劫持按键取得表面上的接管。

| [AOSP TV Input Framework](https://source.android.com/docs/devices/tv) | TV App、TV Input Manager、Provider、Input HAL 分工；系统与第三方输入权限不同 | 电视信号、节目与硬件输入独立适配 | 普通安装无法取得系统 TV App 的全部权限；不能承诺直接控制每个 HDMI 或内置调谐器 |

## 分层与落点

| 层 | 职责 | 从现有实现迭代 |
| --- | --- | --- |
| 电视 Shell | 标准版/爸妈版、一级入口、遥控焦点、通知面板、离线首页、回到原系统 | 保留两版体验，把设备动作与展示代码分离，不全量重写 |
| 共用能力核心 | 应用、媒体/NAS、家庭内容、消息、场景与设备状态，定义输入输出、错误和权限 | 复用模型、领域服务、NAS 和应用操作状态，避免 UI/MCP 各建副本 |
| 电视执行端 | 本机动作、安装器交接、播放焦点、断网恢复、结果核对 | 演进原生类和前台授权窗口；常驻服务另行设计与验证生命周期 |
| 设备适配 | Android 公开接口、小米固件公开入口、可选 OEM/系统模块 | 按能力探测与失败状态选择实现，不在页面里散落机型判断 |
| 家庭服务与 Agent | NAS/电脑可部署的协调服务，配对、授权、同步、MCP、审计 | 延续 WorkBuddy 示例与可撤销授权；与是否设置默认桌面解耦 |

这是职责边界，不要求每层成为独立进程。先按模块演进，确认实际故障与资源成本后再拆服务。

### 能力契约（拟定，尚未实现新接口）

每项能力报告 `id`、契约版本、`status`、执行端、所需授权、原因和证据时间。状态区分 `available`、`needs_authorization`、`unsupported`、`unknown`；可解析 Intent 只算入口可达，不算控制或唤醒实测通过。

首批覆盖桌面候选/返回、应用发现/启动/安装/卸载、NAS 浏览与播放、通知、原生设置、语音共存。平台签名、特权白名单、设备所有者权限分别判断。局域网地址只作连接条件，不作用户身份；二维码握手后记录可撤销凭证，不以“同一 Wi-Fi”替代授权。

人和 Agent 调用同一能力服务。自托管沿用明确授权范围；未来 Hub 托管入口沿用独立 Agent 权益与个人中心管理，不公开私有 Skill。写入保留幂等键、版本冲突、设备归属和撤销校验；安装/卸载保留系统确认，结果未知先查询，不重复提交。

## 三条运行路线

1. **原固件共存版，近期主线。** 用户主动选择是否作为 HOME，逐步承接首页、应用、家庭通知和 NAS 媒体。撤销授权仍能返回原系统；离线可打开本机入口，家庭数据可用范围与过期状态明确显示。
2. **系统扩展版，条件分支。** 仅在指定机型、明确授权与系统集成条件下研究设备管理或 OEM 特权模块。权限白名单与平台签名不能通过扫码授予；设备所有者模式不等于任意系统权限。依据：[AOSP 特权权限白名单](https://source.android.com/docs/core/permissions/perms-allowlist)。
3. **定制固件版，远期研究。** 前置条件为可用的解锁/恢复途径、内核/BSP/驱动、签名和更新方案，以及小米生态保留的可行性。缺乏证据时不发布通用刷机命令、不宣称全机型支持。无法保留原生体验时，不能当成共存版的等价升级。

[AOSP HDMI-CEC 服务](https://source.android.com/docs/devices/tv/hdmi-cec) 涉及系统服务与 HAL；电源、输入和待机唤醒不能靠通用桌面 APK 承诺接管。需要系统权限的目标保留在路线图，单独跟踪实现条件。

## 实施顺序与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| F1 能力层 | 梳理原生动作与权限，统一能力报告和适配接口 | 支持/待授权/不支持/未知分开；无权限时提供原系统入口；不扩大旧令牌 |
| F2 日常 Shell | 可选默认 HOME、恢复流程、应用入口与家庭通知，两版共用能力 | 重启、升级、断网、撤销 HOME 和卸载后可回原系统；本机入口不依赖电脑在线；小爱/电源/音量无回归 |
| F3 家庭服务 | NAS 媒体、Agent 编排、通知与场景、受控扩展契约 | WorkBuddy 改布局/内容并独立回读；NAS 断线/撤销/恢复与播放中断；来源检测不以 HTTP 200 冒充可播放 |
| F4 系统扩展验证 | 一款具备条件的小米电视的独立系统适配分支 | 明确新增权限、恢复路径、失败策略与原生态对照结果；达不到条件保持研究状态 |

每阶段同时覆盖人和 Agent。核心闭环：“回家 → WorkBuddy 根据授权调整场景和家庭信息 → 电视显示 → 遥控器接管 → 原生小爱仍能使用”。先验证动作与回执，不通过后台无限轮询或无障碍点击模拟框架能力。

NAS 继续作为核心：SMB 2/3、WebDAV、Jellyfin 等能力按现有实现与后续验证说明；小米只针对用户指定的新款存储，海康、绿联及其他兼容设备按协议与真实型号分别登记。品牌不等于全部型号兼容，不编造用户数最多的品牌结论。

## 视觉精修

保持深色玻璃、大日期时间、简短客观入口、4K 背景和电视遥控布局，不重新换主题。下一轮具体落实：

- 统一表面、边沿、高光、遮罩层级，正文优先可读，不让动态照片破坏对比。
- 图标统一笔画、网格、光学大小与焦点态，核心入口远距离能区分。
- 标准版保留照片/数据/信息/工具分区；爸妈版维持三大观看入口和较小的常用应用入口，复杂配置由家人或授权 Agent 完成。
- 按设备分档。Android [RenderEffect](https://developer.android.com/reference/android/graphics/RenderEffect) 从 API 31 提供，不能作为 Android 8 的通用实现，也不能把 View 模糊等同于跨应用背景采样。旧设备优先预模糊自有背景、局部合成和实底回退；保留减少透明/动态。
- 对比两版真实截图与焦点路径；帧时间、内存、温度、原生播放另做真机测量，不承诺全机型 4K60。
