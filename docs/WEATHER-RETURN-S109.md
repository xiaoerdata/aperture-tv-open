# 天气返回到开视首页

> 本文保留该阶段的开发记录，改动已合入v43；安装与验收范围见[v43说明](RELEASE-V43.md)。

用户反馈：打开天气后返回，会直接到小米原桌面，没有“已停止运行”提示。因此本轮按“错误离开开视”调查，不能仅根据现象判为应用进程崩溃。

当前为标准版源码修复，未打包、未上传；爸妈版不变。没有连接小米电视，也没有这次操作的 logcat 或 Activity 任务栈记录，尚未证明设备上的唯一触发条件。

## 发现与修复

网页首页的天气关闭本身没有跳转系统桌面：返回关闭天气浮层并恢复入口焦点。原生风景首页则通过独立 `AmbientActivity` 显示天气。此前它完全依赖 JS 回答返回操作，退出时只有 `finish()`，没有检查是否仍有开视首页在任务栈里；WebView 获得焦点时，返回键也没有在分发入口统一处理。

本轮调整：

- 原生天气页的遥控返回在 Activity 分发入口拦截，按下和松开均消费；直接关闭子页面，不等待天气 JS。网页里的返回按钮仍走固定的子页关闭动作。
- 正常任务栈继续恢复现有开视首页；若天气页面是任务根，则先打开开视 `MainActivity` 再关闭天气页。目标为应用内首页，不调用小米桌面，不修改系统默认桌面设置。
- 返回只执行一次，销毁时清除页面引用与待办。屏保设置仍允许网页先处理返回，但等待最多600ms；重复返回立即关闭，迟到回调与后台回调不再触发退出。
- WebView 渲染进程失效时立即分离并销毁该实例，后续暂停、恢复、按键和页面完成回调不得再访问。关闭采用已有 `WebViewDisposal`，保证只销毁一次。
- 子天气页不再调用影响全部 WebView 的 `pauseTimers()`；保留进入时的恢复和该页面自己的暂停、JS计时与天气请求取消。

原生天气返回没有改变首页布局、天气数据源、系统 Home 键或小爱语音处理。

## 证据

从公开仓库固定提交 `0e9c37975c4f82572c7e93baeabe2f262e358ec1` 读取两份旧代码，保存为最小测试夹具。摘要与上一轮 v42 的编译输入也相同。将原生产 `AmbientActivity` / `AmbientWeb` 放入明确的 JVM Android 框架替身后，确认：

1. 旧页面成为任务根、JS回答未处理返回时，只执行结束，没有重建应用首页。
2. 模拟渲染进程失效后，旧暂停回调会访问已失效 WebView；渲染失效回调内也未立即销毁实例。
3. 原分发入口让返回键继续交给有焦点的 WebView；替身模拟该层消费事件。这证明旧入口缺少统一拦截，不能据此断言小米内核一定采用该行为。

修复后的25项控制流检查通过，包含子页返回、任务根恢复、重复按键、页面返回按钮、600ms兜底、后台与迟到回调、销毁、渲染失效和语音键。运行的是生产Activity与包装代码；Android框架、天气传输与相册存储是替身，没有运行真实渲染进程或小米任务管理器。

浏览器使用合成天气：网页首页经原生JS入口连续打开/返回10次，保留首页地址和天气焦点；七日天气的返回按钮、离线返回正常。独立天气页两种返回都只发出一次 `aperture://ambient/close`，没有系统桌面动作。截图已查看，仍为原风景首页。

120份Java源码定向编译和29项尺寸案例通过，无Gradle/APK构建。临时类与框架替身自动清理；保留两份旧文件的最小夹具、复现脚本、一张截图和回执。
